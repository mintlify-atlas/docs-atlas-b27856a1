Aether Sync is designed to be embedded as a library inside any Python 3.7+ application, not only run as a standalone interactive process. Because every component — the transport socket, the reliability tracker, the LWW store, and the gossip loop — is an ordinary Python object or function, you can import them directly from `node.py` and `gossip.py`, wire up the three daemon threads yourself, and use the store's public API (`merge`, `get_all`) from the rest of your code without touching the interactive user loop at all.

## Basic Embedding

The snippet below mirrors the integration example from the README and shows the minimum wiring needed to join a cluster, pre-seed the store with a value, and read it back.

```python
import time
import threading
from node import transport, store, reliability, peers
from gossip import gossip_loop

# ── Identity ────────────────────────────────────────────
node_id = "my-service-1"
port    = 5001

# ── Peer registration ───────────────────────────────────
peers.append(("192.168.1.2", 5001))
peers.append(("192.168.1.3", 5001))

# ── Write a value into the distributed store ────────────
store.merge({"config:db_host": ("postgres.internal", time.time(), node_id)})

# ── Read it back (returns a plain dict) ─────────────────
config = store.get_all()
print(config["config:db_host"])
# → ("postgres.internal", 1678156800.234, "my-service-1")
```

<Tip>
  `store.get_all()` returns a shallow copy of the internal dict, so it is safe to iterate or pass to other threads without holding the store's mutex. Each value is a 3-tuple `(value, timestamp, node_id)` — access the raw string with `config["config:db_host"][0]`.
</Tip>

## Thread Architecture

Aether Sync requires three long-running daemon threads to be active for a node to fully participate in the cluster. When you run `node.py` directly these are started for you at the bottom of the file; when embedding you must start them yourself before your application enters its main loop.

```python
import threading
from node import transport, store, reliability, listener, retry_loop
from gossip import gossip_loop
from node import peers

# 1. Listener — receives all incoming UDP messages and dispatches
#    PUT / GOSSIP / ACK to the appropriate handler.
threading.Thread(target=listener,   daemon=True).start()

# 2. Retry loop — wakes every second, re-sends any PUT or GOSSIP
#    that has not been ACK-ed within RETRY_INTERVAL (default 2 s).
threading.Thread(target=retry_loop, daemon=True).start()

# 3. Gossip loop — broadcasts the full store snapshot to every
#    peer every GOSSIP_INTERVAL seconds (default 3 s).
threading.Thread(
    target=gossip_loop,
    args=(peers, store, reliability),
    daemon=True,
).start()
```

All three threads are marked `daemon=True`, which means they are automatically killed when the main thread exits — no explicit shutdown logic is required for clean process termination.

| Thread | Source | Responsibility |
|--------|--------|----------------|
| `listener` | `node.py` | Blocks on `transport.recv()`; dispatches PUT / GOSSIP / ACK |
| `retry_loop` | `node.py` | Polls `reliability.pending` every 1 s; re-sends stale messages |
| `gossip_loop` | `gossip.py` | Sleeps `GOSSIP_INTERVAL` s; broadcasts `GOSSIP` to all peers |

<Note>
  The listener thread performs blocking I/O on a single UDP socket. It processes one message at a time, so avoid doing expensive work inside `Store.merge()` — the lock is held for the duration of each merge.
</Note>

## State Persistence

Aether Sync's store is entirely in-memory; its contents are lost when the process restarts. To survive restarts, snapshot the store to disk before shutdown and restore it on startup. Because `Store.merge()` is idempotent, loading a snapshot is safe even if the node has already received some of the same keys via gossip.

### Snapshot to disk

```python
import json

# Capture the full store as a plain dict of lists.
# (Tuples become JSON arrays automatically.)
snapshot = store.get_all()

with open("state_backup.json", "w") as f:
    json.dump(snapshot, f)
```

### Restore from snapshot

```python
import json

with open("state_backup.json", "r") as f:
    restored = json.load(f)

# merge() converts each incoming list back to a tuple via tuple(incoming).
store.merge(restored)
```

The round-trip works because `Store.merge()` calls `tuple(incoming)` on every value it receives, so the JSON arrays produced by `json.dump` are automatically converted back to `(value, timestamp, node_id)` tuples on load.

<Tip>
  Register a `signal.signal(signal.SIGTERM, ...)` handler that calls the snapshot code before exiting, so that graceful pod shutdowns in Kubernetes or `systemctl stop` invocations always persist state.
</Tip>

## Key Naming Patterns

Aether Sync places no constraints on key format — any non-empty string is accepted. In practice, **colon-delimited namespaced keys** prevent collisions between different subsystems sharing a single cluster:

```
<service>:<resource>:<field>
```

Examples from the README and source:

| Key | Description |
|-----|-------------|
| `user:42:name` | The `name` field of user record 42 |
| `user:42:email` | The `email` field of user record 42 |
| `config:db_host` | Database host for the `config` namespace |
| `counter` | A bare unnamespaced key (discouraged in shared clusters) |

<Tip>
  If multiple independent services embed Aether Sync on the same cluster, prefix every key with the service name (e.g. `auth:session:abc123` vs. `catalog:product:999`) to prevent one service's writes from clobbering another's.
</Tip>

## FAQ

<Accordion title="Why UDP instead of TCP?">
  UDP has significantly lower per-message overhead than TCP: there is no connection handshake, no stream-level flow control, and no head-of-line blocking. For a gossip-based system that already tolerates and recovers from packet loss, the reliability guarantees built into TCP are redundant — they would add latency and state without providing any additional correctness benefit. Aether Sync's reliability layer reconstructs the delivery guarantees that matter (at-least-once delivery of PUT and GOSSIP) directly on top of UDP, while avoiding TCP's costs. The result is that a single process can handle 1 000–10 000 operations per second on commodity hardware with sub-5 ms one-hop latency on a local network.
</Accordion>

<Accordion title="How do I handle larger data structures?">
  The store's `value` field is always a plain string on the wire. To store a dict, list, or any other structure, serialize it to a JSON string before insertion and deserialize it after retrieval:

  ```python
  import json, time

  node_id = "my-service-1"

  # Write a nested object
  payload = {"host": "postgres.internal", "port": 5432, "ssl": True}
  store.merge({"config:db": (json.dumps(payload), time.time(), node_id)})

  # Read it back
  raw_value, ts, origin = store.get_all()["config:db"]
  db_config = json.loads(raw_value)
  print(db_config["port"])  # → 5432
  ```

  Keep in mind that the entire GOSSIP message (full store snapshot) must fit within `BUFFER_SIZE` (default 4 096 bytes). If your serialized values are large, consider increasing `BUFFER_SIZE` in `config.py` or distributing data across more granular keys.
</Accordion>

<Accordion title="What happens if my clock goes backwards?">
  Aether Sync uses `time.time()` (the system wall clock) as the primary ordering key for LWW conflict resolution. If a node's clock jumps backwards — due to an NTP correction or a misconfigured VM — a write made after the jump will appear to have an older timestamp than writes made before it, and will lose the LWW race against those earlier records even if it is causally newer.

  The node ID tiebreaker (`inode > n` in `Store.merge()`) still guarantees **deterministic** resolution (no split-brain), but **causality may be violated**: a logically newer write can be silently discarded. To mitigate this:

  - Run NTP or `chronyd` on all nodes to keep clocks within a few milliseconds of each other.
  - Avoid large manual clock adjustments on running nodes.
  - For stronger causality guarantees, the README recommends migrating to **hybrid logical clocks (HLC)**, which combine physical time with a logical counter to preserve happens-before ordering even under moderate clock skew.
</Accordion>

<Accordion title="Can I use this in production?">
  Aether Sync is a clean, fully functional reference implementation and an excellent foundation for a production system, but several gaps should be addressed before deploying it in a critical path:

  - **No persistent storage** — state is lost on restart. Add a snapshot-on-shutdown routine (see the State Persistence section above) or back the store with SQLite or RocksDB.
  - **No authentication or encryption** — all messages are plaintext. Wrap the UDP socket with a WireGuard tunnel or add HMAC-SHA256 message signing before exposing nodes across untrusted networks.
  - **No tombstone support** — deleted keys cannot be permanently removed. Use a sentinel value (e.g. `"__DELETED__"`) as a convention until tombstone support is added.
  - **No ACK queue TTL** — if a peer disappears permanently the `pending` dict grows without bound. Add a configurable message TTL to prevent memory exhaustion in long-running processes.
  - **Fixed retry interval** — the 2-second flat retry can overwhelm the network under extreme loss. Implement exponential backoff with jitter for production resilience.

  For workloads where these trade-offs are acceptable (internal tooling, low-traffic config propagation, development clusters), Aether Sync works well as-is.
</Accordion>

---

<Warning>
  Aether Sync transmits all messages — including key names, values, timestamps, and node IDs — as **unencrypted, unauthenticated plaintext UDP datagrams**. There is no TLS, no HMAC signature, and no peer allowlist. Any host that can reach a node's UDP port can read the full store contents (via a spoofed GOSSIP exchange) or inject arbitrary key-value pairs. **Do not expose Aether Sync node ports on public interfaces or untrusted network segments without adding an encryption and authentication layer** (such as a WireGuard mesh, IPsec, or a custom HMAC signing wrapper around `Transport.unreliable_send()`).
</Warning>
